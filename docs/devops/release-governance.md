# Релизный цикл и стратегия разработки

**Версия**: 1.0.0

---

## 1. Краткий обзор

Мы используем **GitHub Flow** с еженедельными релизами по **четвергам**.
Каждаяя фича разрабатывается в отдельной ветке, проходит код-ревью перед влитием в `master`.
Релизный процесс автоматизирован через **GitLab CI/CD**, время деплоя - *TBD*

---

## 2. Стратегия ветвления

### Основные ветки
| Ветка | Назначение | Защита |
|-------|------------|--------|
| `main` | Продакшен-код. Всегда стабильна. | Прямой пуш запрещен. Только через PR. |

### Ветки для фич
- Формат: `feature/short-description`
- Пример: `feature/add-payment-gateway`
- Создаются от: **`master`**
- Сливаются в: **`master`**
- Живут не дольше: **5 рабочих дней** (если дольше - обсуждаем с тимлидом)

### Ветки для хотфиксов
- Формат: `hotfix/{{TICKET-ID}}-critical-fix`
- Создаются от: **`master`**
- Сливаются в: **`master`**

---

## 3. Процесс разработки фичи

### Шаги:
1. Создать ветку от `master`.
2. Разработать фичу, локально запустить тесты.
3. Создать Pull Request (PR) в `master`.
4. PR должен пройти:
   - ✅ Код-ревью (минимум 1 апрув)
   - ✅ CI-пайплайн (линтеры, юнит-тесты, сборка)
   - ✅ Проверка покрытия тестами (минимум 80%)
5. После влития - автоматический деплой на **Staging**.
6. Тестирование на Staging (ручное или авто). 

### Что делать при конфликтах?
- Решать локально через `git rebase master`.
- **Запрещено** использовать `git merge` для синхронизации с основной веткой.

## 4. Стратегия релизов (Release Strategy)

### Релизный цикл
| Тип релиза | Частота | День недели | Время |
|------------|---------|-------------|-------|
| **Плановый** | Еженедельно | Четверг | 10:00 UTC |
| **Хотфикс** | По требованию | Любой день | Сразу после фикса |

### Как происходит релиз:
1. В `master` накопились фичи, прошедшие Staging.
2. CI автоматически собирает Docker-образ с тегом `latest` и версией коммита.
3. Деплой на **Production** идет **поэтапно**:
   *===TBD===*
   - 10% трафика
   - Наблюдение за метриками 30 минут
   - 100% трафика
   *===TBD===*
4. В случае ошибок - автоматический откат до предыдущего стабильного тега.

### Версионирование
Мы используем **Semantic Versioning**:
- `MAJOR` (несовместимые изменения)
- `MINOR` (новая функциональность, совместимая)
- `PATCH` (багфиксы)

Теги создаются автоматически при релизе: `v1.2.3`.

## 5. Окружения и CI/CD

| Окружение | URL | Назначение | Деплой из ветки |
|-----------|-----|------------|-----------------|
| **Dev** | dev.example.com | Разработка (каждый PR создает свой стенд) | `feature/*` |
| **Staging** | staging.example.com | Тестирование перед релизом | `master` (после каждого влития) |
| **Production** | example.com | Живой пользовательский трафик | `master` (по расписанию) |

### Quality Gates
- Юнит-тесты: 100% прохождение.
- Интеграционные тесты: 100% прохождение.
- Сканирование безопасности: без критических уязвимостей.
- Покрытие кода: > 80%.

## 7. Ответственность и коммуникация

| Роль | Ответственность |
|------|-----------------|
| **Developer** | Написать код, провести локальное тестирование, создать PR. |
| **Tech Lead** | Утвердить архитектуру фичи, помочь с ревью. |
| **QA Engineer** | Проверить фичу на Staging, запустить регресс-тесты. |
| **DevOps** | Настроить пайплайн, мониторинг, выполнить откат. |

### Каналы коммуникации при релизе:
- **Чат:** Slack-канал `#releases` - уведомления о начале/окончании релиза.
- **Мониторинг:** Grafana - отслеживание ошибок в реальном времени.

## 9. FAQ

**Вопрос:** Можно ли закоммитить напрямую в `master`?  
**Ответ:** Нет. Только через PR с апрувом.

**Вопрос:** Что делать, если срочный хотфикс, а время - 2 часа ночи?  
**Ответ:** Создать ветку `hotfix/...`, сделать PR с объяснением, после апрува - деплой. После релиза обязательно влить хотфикс в `master`.

**Вопрос:** Как долго живет ветка фичи?  
**Ответ:** Не больше 5 дней. Если дольше - нужно перебазироваться от `master` и объяснить задержку тимлиду.
